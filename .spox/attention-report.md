# Attention report

## Intent
Specs that are built but never verified, or started and never finished, pile up unnoticed. `spox attention` is a small maintenance report for that: run from a project directory, it prints nothing when there is nothing to flag, and otherwise a compact, stable text report of the oldest `ongoing` and `pending-verification` specs, ending with one instruction line for an agent. It is meant to be called by a separate SessionStart hook (the user's own hooks folder, written later and not part of this spec) whose output is passed to the agent unchanged, so it must be fast, read-only and predictable.

## Acceptance criteria
- [ ] `spox attention` considers only specs whose status is exactly `ongoing` or `pending-verification`
- [ ] `spox attention` only runs where spox is set up: it needs a `.spox` at or above the current directory (the project containing it, found by walking up as spox does today). With none, it does nothing — it never searches below the current directory or the git root for projects — so a monorepo whose top folder has no `.spox` is not scanned, and its sub-projects stay isolated; each reports only when called from inside it
- [ ] Scope is `all` by default and is anchored at the current directory, never the git root: the containing project plus every `.spox` found below the current directory with the existing search rules (depth 5, skipping hidden dirs, `node_modules`, `target`, symlinks). From inside a sub-project that is just that project (sibling projects are not scanned); from a monorepo top folder that has its own `.spox`, it is the top project and every sub-project beneath it
- [ ] `--scope nearest` or `SPOX_ATTENTION_SCOPE=nearest` restricts it to the containing project only, with no downward scan. `--scope all` / `SPOX_ATTENTION_SCOPE=all` is the default; the flag wins over the env var; `-C` and `SPOX_PROJECT` still set the starting directory; any other scope value prints an `error:` line to stderr and exits 1, like every other spox usage error
- [ ] When no spec qualifies in any scanned project, or no `.spox/` is found at or above the current directory, it prints nothing to stdout or stderr and exits 0; a runtime error in one project (unreadable folder, git failure) is skipped silently and never makes the command fail or print noise
- [ ] It is read-only and quiet: it writes no files (no cache, no skill install, no `.spox/` changes), does not run the daily self-update check or the skill auto-update, and does not print the nested-discovery stderr note
- [ ] A qualifying spec is either *committed* (tracked by git and unchanged since its last commit) or *uncommitted* (untracked, or with staged or unstaged changes); uncommitted specs are reported as their own category and get no age
- [ ] The report is a tree grouped by project, with the box characters `spox list -c` uses: each project that has a listed spec is a header line, followed by its specs indented two spaces and prefixed `┣━ ` (`┗━ ` for the last one in that project). Headers are printed even when only one project was scanned, so the report always has one shape. The project containing the current directory is named by its own folder name; other projects by their path relative to the current directory (e.g. `services/api`). Git calls for each project run in that project's own directory, so nested git repos work
- [ ] When something qualifies, the first line is `spox attention: <N> spec(s) need a look` where `<N>` is the total number of qualifying specs, committed and uncommitted (singular `1 spec needs a look` when N is 1)
- [ ] At most 5 committed specs are listed across all projects, oldest first (ties by project, then name). Within a project they appear oldest first, and projects are ordered by their oldest listed spec (projects with only uncommitted specs come last, by name). A spec line is `<name>  <status>  <age>d  <open> open` — fields separated by exactly two spaces, no padding; `<age>` is whole days and `<open>` is the number of unchecked `- [ ]` criteria
- [ ] Uncommitted specs appear in their own project's group after its committed ones, sorted by name, with `uncommitted` in place of the age (`<name>  <status>  uncommitted  <open> open`); at most 5 uncommitted specs are listed across all projects
- [ ] When specs are left out by the two caps, a line `…and <K> more` follows the tree, where K is the total number not shown
- [ ] The report's last line is exactly: `Agent: mention this briefly at a natural moment, offer to go through it, and do not change any spec without asking.`
- [ ] For a committed spec, age is the time since its last git commit (`git log -1 --format=%ct -- <file>`), never negative; only if the project is not in a git repo, or git is unavailable or fails, is the file's modified time used for every qualifying spec and nothing is reported as uncommitted
- [ ] Output is byte-for-byte stable for identical input (no timestamps, colour, or glow), so a hook can pass it through unchanged
- [ ] The command is covered by tests (temp git project, no self-update triggered) for: nothing to report, no `.spox/`, fewer than 5 specs, more than 5 specs with the `…and K more` line, ordering oldest first, an untracked spec and a modified spec each marked `uncommitted`, the no-git mtime fallback, a monorepo with two sub-projects under the default scope (project headers, merged ordering), `--scope nearest` / `SPOX_ATTENTION_SCOPE`, and an invalid scope value
- [ ] `spox help`, `readme.md`, and the `spox` skill (`skills/spox/SKILL.md`, then `spox skill install`) document `attention`, and `Bash(spox attention)` is added to the skill's `allowed-tools` and to the allow list that `spox init` writes into `.claude/settings.local.json`

## Non-goals
- The new "watching" / "shipped, watching" status, priority lanes, or a "next" command
- Daily or session throttling — the calling hook handles that
- Any change to self-update behaviour beyond `attention` not triggering it
- Writing the hook script or any `settings.json` / hook wiring
- Reporting `draft` specs, or filtering/limiting options (`--limit`, `--all`, `--json`) — v1 is fixed at the format above

## Notes
- Age choice: the frontmatter only records a creation date, which says little about staleness (an old spec that was just worked on would look stale). Last git commit touching the file approximates "last time anyone touched this spec". It depends on history being present (a shallow clone reports the clone date), and falls back to mtime only outside git.
- Output is a tree rather than `path:name` prefixes: it reads better for people and agents, and reuses the `┣━`/`┗━` look of `spox list -c`. Always printing the project header keeps one output shape.
- Uncommitted specs are their own category rather than getting a guessed age: specs should be committed once finalized so they are tracked in the repo, so an `ongoing` or `pending-verification` spec that is untracked or modified is itself something to flag, and mtime would be a misleading age for it. Only `ongoing` / `pending-verification` specs are checked; an uncommitted `draft` is normal and not reported.
- Cost: per qualifying spec, one `git log -1` and (only if it has a commit) one `git status --porcelain`, plus one `git rev-parse` per project. All are local and read-only (`GIT_OPTIONAL_LOCKS=0` stops `git status` from refreshing the index). Spec directories are small, so this should stay fast; measure it by hand before relying on it in a hook.
- Scope default is `all` because monorepo sessions typically start at the top folder and never inside the sub-projects, so work there would otherwise go unnoticed. It only applies where the top folder is itself set up with spox; `nearest` gives a quiet, single-project report for users who want one. The user's own hook can pass `--scope nearest` or set the env var, so no config file is introduced.
- The scope is anchored at the current directory, not the git root, so a session inside one sub-project does not report its siblings, and a session at the monorepo top reports everything beneath it. "Digging upwards" is limited to the existing walk that finds the project the current directory belongs to.
- Not a reuse of `discover()` as is: spox's general discovery falls back to a single `.spox` below the git root when none is above. `attention` deliberately does not. A folder without spox set up is out of scope, and a monorepo's top folder is treated as orchestration the user chose not to manage with specs unless it has its own `.spox`. Use `find_spox_above` plus `collect_spox_below` from the containing project's directory, not the git-root fallback.
- Open question: projects nested inside another project are not found (the existing downward search stops at the first `.spox` it meets); v1 keeps that rule.
- Cost: scanning is the existing bounded downward search plus the git calls below, repeated per project; with many projects this is the part to measure before relying on it in a hook.
- Today `main()` calls `maybe_self_update()` before dispatch, and `maybe_update_skill(false)` runs on several commands. `attention` must dispatch before or around those so a SessionStart hook never triggers a `git pull`, rebuild or file write; this is the only touch on self-update and stays within the non-goal above.
- Integration points in `src/main.rs`: (1) `main()` calls `maybe_self_update()` before parsing arguments, so `attention` has to be recognised first (a small reorder of `main`); (2) do not use `require_spox_dir()` — it calls `sync_format_md()`, which writes `.spox/.format.md` and prints to stderr, and exits 1 on errors, all of which break "read-only, quiet, exit 0"; (3) the spec-reading loop inside `cmd_list` should be pulled out into a shared helper so `attention` and `list` read specs the same way; (4) add `attention` to `known_cmds` in the fallback arm so wrong arguments give the standard "unexpected arguments" error.
- Git detail: an empty `git log -1` result means the file is untracked, so treat it as uncommitted; spox already shells out to git (`git_pull`, `git_head`), so this follows existing practice. Tests need real `git init` repos (the existing sandbox only fakes a `.git` directory) and `GIT_COMMITTER_DATE` to control commit ages.
- Reuse `apply_project_option` (`-C`, `SPOX_PROJECT`) and the directory-walking helpers from nested-project-discovery, and the existing `Spec` parse (`open_criteria`) rather than re-parsing. nested-project-discovery is still `ongoing`; this depends on its code, which is already merged.
- Order of the report relies on exact status strings, not `status_group()`'s substring matching.
- zsh-completion's planned `KNOWN_COMMANDS` constant and its static completion check will need `attention` added (and `known_cmds` at `src/main.rs:1245` today).
